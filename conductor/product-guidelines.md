# Product Guidelines

## 1. Communication Tone and Style

The project's external communication and documentation will adopt a **Formal and Academic** tone and style. This approach emphasizes precision, detailed technical explanations, and references to academic work, aligning with the project's scientific origins and complex technical domain.

## 2. Visual Identity and Branding

A **Consistent Logo and Color Palette** will be maintained across all project materials. This ensures strong brand recognition and consistency, leveraging established branding elements from the `README.md` and documentation (e.g., specific shades and styles from badges and logos).

## 3. Content and Feature Presentation

To effectively cater to a diverse target audience, including academic researchers, FCN designers, and Python developers, the project will implement **Layered Documentation**. This involves providing high-level overviews for quick understanding, complemented by deep dives into technical details and academic references for researchers and those seeking in-depth knowledge.

## 4. Core Principles for Contributing

Contributions to the `fiction` project must adhere to the following core principles to ensure its long-term health, quality, and maintainability:

- **Comprehensive Testing:** All new features and modifications must be accompanied by thorough unit tests. This is essential for ensuring correctness, preventing regressions, and maintaining the overall stability of the codebase.
- **Strict Adherence to Coding Standards:** Contributions are expected to strictly follow the established C++ and Python coding standards, including formatting, naming conventions, and documentation guidelines as detailed in the `AGENTS.md` file. This ensures consistency and readability across the entire codebase.
- **Clear and Detailed Commit Messages:** All commits should include clear, descriptive messages that explain both _what_ changes were made and _why_ they were necessary. This practice significantly improves the codebase's history and facilitates understanding for other contributors.

## 5. Proposing Changes and Features

The preferred processes for proposing and discussing new features or significant changes to the project are:

- **GitHub Issues and Discussions:** Proposals should primarily be initiated through GitHub Issues or Discussions. This approach fosters an open and collaborative environment, allowing for community feedback and transparent decision-making, which is standard practice for open-source projects.
- **Direct Pull Requests:** Contributors are also encouraged to submit direct pull requests with their proposed changes. While discussions often occur during the pull request review process, it is advisable to consider using GitHub Issues or Discussions for broader conceptual discussions or significant architectural changes beforehand to ensure alignment with project goals.
