# Specification: A Physical Design Algorithm for Pin Unscrambling

## 1. Introduction

This document specifies the requirements for implementing a new physical design algorithm within the `fiction` framework. The algorithm's purpose is to "unscramble" or reorder the input and output pins of an existing, fully placed and routed gate-level layout. This functionality is crucial for interfacing with external tools and adhering to fixed pin constraints, behaving similarly to a post-layout optimization task.

## 2. Problem Statement

Gate-level layouts generated by physical design algorithms often have their input and output (I/O) pins in an order determined by the placement and routing process. This ordering might not match the desired or required pin configuration for system integration. A mechanism is needed to transform the layout's current I/O ordering to a user-specified target ordering by inserting a network of wires and crossings.

## 3. Goals

- To develop a new physical design algorithm that can reorder the I/O pins of a given gate-level layout.
- The algorithm must operate on an already placed and routed layout, modifying it, i.e., adding these unscrambling networks at the inputs and outputs, to match the desired pin permutations.
- The solution should be implemented as a standard `fiction` physical design algorithm, located under `include/fiction/algorithms/physical_design/`.
- The initial implementation will focus on hexagonal, pointy-top, row-wise clocked layouts, with the potential for future expansion to other layout topologies like Cartesian.

## 4. Requirements

### 4.1. Functional Requirements

- **FR1: Algorithm Signature:** The algorithm shall accept as input:
  - A `fiction::gate_level_layout` as a template parameter `Lyt` similarly to post-layout optimization.
  - A desired input pin ordering (i.e., `std::vector<mockturtle::node<Lyt>>`).
  - A desired output pin ordering (i.e., `std::vector<mockturtle::node<Lyt>>`).
- **FR2: Unscrambling Logic:** The algorithm must be able to generate a permutation network using only wire and crossing elements to connect the layout's original pin locations to new locations that satisfy the target ordering. This will increase the layout size towards the top (for inputs) and bottom (for outputs). The layout must be resized accordingly. Since coordinates are unsigned, the layout must be moved towards the bottom to make space for the input ordering, or, probably better, a new layout must be created that first sets up the input pin ordering, then pastes the original layout, and then sets up the output ordering. The pins will hence move to the beginning (for PIs) and end (for POs) of those wire networks, respectively. Moving pins can be achieved via the `move_node` function of `gate_level_layout`. Explore the tests for examples.
- **FR3: Functional Correctness Preservation:** The transformed layout must remain functionally equivalent to the original one. The unscrambling network should only consist of wires and crossings, not logic gates. Functional correctness must be tested via `fiction::equivalence_checking` in tests.
- **FR4: Layout Topology Focus:** The initial implementation must correctly handle **pointy-top hexagonal gate-level layouts with row-wise clocking**.
  - In this topology, information flows downwards: a tile can drive its bottom-right and bottom-left neighbors.
- **FR5: Input and Output Handling:** The algorithm shall support reordering of input and output pins.

### 4.2. Non-Functional Requirements

- **NFR1: Performance:** The algorithm must be highly efficient for practical use cases.
- **NFR2: Maintainability:** The code must adhere to `fiction`'s C++17 coding standards (`snake_case`, Doxygen, `const`-correctness).
- **NFR3: Testability:** The implementation must be thoroughly tested using `Catch2`. Unit tests should cover the core logic, and integration tests should verify the algorithm on sample layouts. See existing algorithms' tests like post-layout optimization.
- **NFR4: Error Handling:** The algorithm should handle cases where a reordering is not possible within the given layout constraints and report errors clearly. Furthermore, user error must be caught, if e.g., the passed vectors of nodes contain non-I/O pins or are not complete.
- **NFR5: Documentation:** Doxygen documentation is required for all new symbols, functions, and classes.

## 5. Scope

**In Scope:**

- Researching and implementing a suitable permutation or sorting network algorithm.
- Implementing the algorithm for pointy-top hexagonal layouts.
- Verifying the functional equivalence of the transformed layouts in the tests.

**Out of Scope:**

- Support for other layout topologies (e.g., Cartesian) in the initial version, though the design should allow for future extension.
- Automatic discovery of an "optimal" pin ordering. The target order is a required input. First check whether this problem is NP-complete. In that case, we could think about adopting `fiction::color_routing` for this purpose, which is an exact negotiation router.

## 6. Open Questions / Dependencies

- Which permutation/sorting network (e.g., Beneš, butterfly, bitonic) is most suitable for implementation in a hexagonal grid with limited connectivity?
- How can the `fiction::gate_level_layout` API be used to effectively query pin locations and modify the layout by adding wire and crossing segments?
- How to best minimize layout area and path length overhead introduced by the unscrambling network.
